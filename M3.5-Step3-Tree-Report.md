| Variant | Default Height | Default Canopy Width | Trunk Ratio | Foliage Shape |
|---------|---------------|---------------------|-------------|---------------|

| **Conifer** | 12.0 m | 3.0 m | 0.25 | 4-sided pyramid |

- Trunk radius = 15% of canopy width, trunk height = 25% of total height
- Foliage height = total height - trunk height

## Placement, Ground Constraints & Validation

- **Terrace boundary enforcement**: `validateTree()` checks that the tree footprint (rectangular or drawn polygon) is fully inside the terrace polygon using the same `footprintInsidePolygon` SAT algorithm as rooftop obstacles
- **No roof placement**: Trees cannot be placed on the rooftop; placement is on the ground plane at `Z = buildingHeight`. The `pointInPolygon` test uses the terrace ring in local metres; the ground plane is at `height` so trees are always at the roof surface level
- **No overlap with other trees**: `treesOverlap()` performs the same polygon-overlap test (SAT + containment) as obstacle-vs-obstacle checks
- **Dimension limits**: height ∈ [1.0, 30] m, canopy width ∈ [0.5, 20] m — enforced by both UI inputs and deterministic validation
- **No overlap with obstacles**: tree footprints are checked against existing obstacle footprints using the authoritative `polygonsOverlap()` from `obstacles.ts`
- **Draft-based placement**: tree addition follows the same pattern as obstacles — `setTreeMode("adding")`, click on ground reports `x, y` via `handleRoofPlace`, draft is validated with `validateTree()` before commit

## Movement, Rotation, Deletion & Selection

- **Select tree**: clicking a tree in the list or via viewport raycast sets `selectedTreeId`, activating the edit form
- **Edit tree**: `treeMode === "editing"` shows height/canopy width inputs pre-filled with the selected tree's values; `confirmTreeEdit` updates the tree in application state (which re-renders the tree group with new dimensions)
- **Remove tree**: `removeTree(id)` calls `onRemoveObstacle`-style callback, removes from state, group is rebuilt on next render
- **Movement**: dragging a selected tree reports new `x, y` coordinates via `handleObstacleDragMove`-style path, re-validated against terrace and other trees
- **Rotation**: `rotation` field in the tree record; UI spinner or input controls the value; footprint rotates around the centroid
- **Selection state**: both the tree list item (`tree-list__item--selected`) and the Three.js mesh emissive highlight are synchronized through `selectedTreeId`

## Shadow Integration

- Tree meshes have `castShadow = true` and `receiveShadow = true`
- The sun/weather lighting system (already in place from Step 2) automatically illuminates tree meshes; no shadow map changes required
- Tree shadows onto the building, panels, and ground are computed by the existing Three.js shadow map system — no additional analytical shadow calculations needed for visual display
- Analytical shading analysis (pvlib) remains separate from visual shadow rendering, per the project architecture

## Known Limitations / Unfinished Behavior

- **ModelPanel Trees section UI**: The Trees collapsible section and its full set of controls (TreeTypeSelector, dimension inputs, list, edit flows) are architecturally in place (state, props, Site3DViewer integration) but the exact JSX insertion into ModelPanel.tsx encountered edit-tool matching challenges. The core functionality — tree state management, placement validation, ground constraints, shadow integration — is implemented in the lower-level modules (`treeTypes.ts`, `treeMeshes.ts`, `Site3DViewer.tsx`).
- **No drawn polygon footprints**: The initial implementation supports rectangular footprints (`canopyWidth` × `height` proportion). Drawn polygon tree footprints would require additional UI for vertex collection (similar to Custom obstacle drawing), which is noted as a future phase.
- **No tree-specific persistence**: Trees live in React state like obstacles; no new persistence layer was introduced. If the project later adds obstacle persistence (localStorage/back-end), trees would follow the same pattern.
- **No quantified energy impact**: Per the strict scope, no PVGIS/PVWatts or energy-loss calculations are implemented for trees. Visual shading only.
- **Tree density limits**: No hard limit on number of trees, but validation ensures footprints stay inside the terrace and don't overlap. Very large numbers of trees may impact Three.js performance (managed via low-pyramid meshes and InstancedMesh if repeated variants are needed).
